# UI technology for Rust windows

Resolves [#26](https://github.com/rawasmhd/breakpoint/issues/26). Researched 2026-11-02 against primary sources only (crates.io, docs.rs, the projects' repositories and issue trackers, Microsoft Learn). Every factual claim carries a link; where no source gives a measured number the entry says **unmeasured**.

## 1. Question and constraints

Which technology should breakpoint use for a **settings window** (two pages: reminders with time pickers and checkboxes, work hours), a **first-run wizard**, and possibly a small **custom nudge popup**?

Constraints inherited from `docs/SPEC.md`:

- Rust is locked; the goal is the smallest exe (target 1 to 3 MB) with the least code.
- We run our **own Win32 message loop** on a hidden message-only window and use the **`tray-icon`** crate for the tray. No `winit`.
- Release profile is already `opt-level = "z"`, `lto`, `codegen-units = 1`, `panic = "abort"`, `strip`.
- CI releases are built on `x86_64-pc-windows-msvc`; the dev machine has only the `x86_64-pc-windows-gnu` toolchain, so every candidate must build on GNU too.
- `winresource` is already a build dependency (icon and version info).
- License is MIT.

## 3. Candidates in detail

### 3.1 Raw Win32 dialogs via the `windows` crate

**What it is.** Dialog templates compiled into the exe as resources, created with `DialogBoxParamW` (modal) or `CreateDialogParamW` (modeless), with a dialog procedure handling `WM_INITDIALOG` and `WM_COMMAND`. Microsoft's walkthrough covers both flavours, including the `IsDialogMessage` call a modeless dialog needs in the main loop ([Using Dialog Boxes, Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/dlgbox/using-dialog-boxes)). `DialogBoxParamW` is exposed by the `windows` crate in `windows::Win32::UI::WindowsAndMessaging` ([windows-docs-rs](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/UI/WindowsAndMessaging/fn.DialogBoxParamW.html)).

**Controls we need.** Time pickers are the Date and Time Picker common control with `DTS_TIMEFORMAT` ("Displays the time", default format from `LOCALE_STIMEFORMAT`) plus `DTS_UPDOWN` for a spinner instead of a calendar drop-down ([DTP styles](https://learn.microsoft.com/en-us/windows/win32/controls/date-and-time-picker-control-styles)); values go in and out through `DTM_SETSYSTEMTIME` / `DTM_GETSYSTEMTIME` ([DTP reference](https://learn.microsoft.com/en-us/windows/win32/controls/date-and-time-picker-control-reference)). Checkboxes and radio buttons are `BUTTON` class controls set with `CheckDlgButton` / `IsDlgButtonChecked` as in Microsoft's modeless example ([Using Dialog Boxes](https://learn.microsoft.com/en-us/windows/win32/dlgbox/using-dialog-boxes)).

**Nudge popup.** `TaskDialogIndirect` "creates, displays, and operates a task dialog" with application-defined icons, title, content, command links, push buttons, radio buttons and a verification checkbox, with a callback for notifications; it requires Comctl32.dll version 6 and Windows Vista or later ([TaskDialogIndirect](https://learn.microsoft.com/en-us/windows/win32/api/commctrl/nf-commctrl-taskdialogindirect)). That covers "Done / Snooze 5 min / Skip" without any custom drawing. A fully custom look would be a `WS_POPUP` window drawn by us, which is more code.

**Native look.** Visual styles (the modern look of buttons, checkboxes, the DTP) require declaring Common Controls v6 in the application manifest; without it applications use the classic comctl32 v5 controls ([Enabling Visual Styles](https://learn.microsoft.com/en-us/windows/win32/controls/cookbook-overview)).

**DPI.** Microsoft recommends setting DPI awareness in the manifest, `<dpiAwareness>PerMonitorV2</dpiAwareness>`, rather than by API ([Setting the default DPI awareness](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process)). Under Per-Monitor V2, Windows automatically DPI-scales the non-client area, theme-drawn bitmaps in comctl32 v6 controls, and "Win32 dialogs (from CreateDialog)" ([High DPI Desktop Application Development](https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows)). So dialog-template windows get free scaling; only a hand-built popup window would have to handle `WM_DPICHANGED` itself, using the suggested rectangle the message provides (same page).

**Resources on both toolchains.** `winresource` generates the `.rc` for either Microsoft `rc.exe` or GNU `windres.exe` and locates them automatically ([winresource](https://docs.rs/winresource/latest/winresource/)). Its `WindowsResource` has `set_manifest` / `set_manifest_file` for the comctl32 v6 and DPI manifest and `append_rc_content` to add arbitrary resource script, which is where `DIALOGEX` templates go ([WindowsResource](https://docs.rs/winresource/latest/winresource/struct.WindowsResource.html)). The bitness of the resource compiler must match the Rust toolchain, so GNU 64-bit needs MinGW64 ([winresource](https://docs.rs/winresource/latest/winresource/)).

**Integration with our loop and `tray-icon`.** This is our loop. `tray-icon`'s Windows backend registers its own window class with `RegisterClassW`, creates a hidden window with `CreateWindowExW` and receives tray callbacks as `WM_USER_TRAYICON` messages in that window's procedure ([platform_impl/windows/mod.rs](https://github.com/tauri-apps/tray-icon/blob/dev/src/platform_impl/windows/mod.rs)); the README's only requirement is that "an event loop must be running on the thread" ([tray-icon README](https://github.com/tauri-apps/tray-icon)). A modal `DialogBox` "processes all user input until the user closes the dialog box", that is it runs its own dispatch loop, so the tray window keeps receiving messages while a dialog is up; a modeless dialog needs the `IsDialogMessage` check added to our `GetMessage` loop ([Using Dialog Boxes](https://learn.microsoft.com/en-us/windows/win32/dlgbox/using-dialog-boxes)).

**Maintenance.** `windows` 0.62.2 was published 2025-10-06 under MIT OR Apache-2.0 ([crates.io](https://crates.io/api/v1/crates/windows)); the underlying `windows-core`, `windows-link`, `windows-window` and `windows-webview` moved to 0.100.0 on 2026-09-03 ([windows-core](https://crates.io/api/v1/crates/windows-core), [windows-link](https://crates.io/api/v1/crates/windows-link), [windows-window](https://crates.io/api/v1/crates/windows-window), [windows-webview](https://crates.io/api/v1/crates/windows-webview)). The repository was pushed 2026-11-01 and has 41 open issues (GitHub API, 2026-11-02). Microsoft now also ships `windows-window` 0.100.0 (MSRV 1.95), a thin "create a desktop window and run its message loop" helper with a `pump()` mode for "an external loop owns the wait"; it is explicitly "not a control toolkit" ([windows-window readme](https://github.com/microsoft/windows-rs/tree/master/crates/libs/window)). It could replace hand-written window-class boilerplate for a custom popup if we ever want one.

**GNU target.** `windows-core` 0.62.2 depends on `windows-link` ([dependencies](https://crates.io/api/v1/crates/windows-core/0.62.2/dependencies)), whose `link!` macro "uses `raw-dylib` and thus does not require import lib files" ([windows-link docs](https://docs.rs/windows-link/latest/windows_link/)). Rust stabilised `raw-dylib` for Windows x86_64 in 1.65 and the remaining pieces (`link_ordinal`, `import_name_type`, `-Cdlltool`) in 1.71 ([RELEASES.md](https://github.com/rust-lang/rust/blob/master/RELEASES.md)). The older `windows-targets` crate ships per-target import libs including `windows_x86_64_gnu` and `windows_x86_64_gnullvm` ([windows-targets](https://docs.rs/crate/windows-targets/latest)). No GNU-specific blocker found.

**Exe size delta.** Unmeasured as an absolute, but no new crate is linked: dialogs are data in the resource section and the control classes live in `user32`/`comctl32`. This is the only candidate whose cost is bounded by the size of our own code.

### 3.2 `native-windows-gui` (NWG)

**What it is.** "A very light wrapper over WINAPI" exposing the Win32 control library; the README lists a date-time picker (`datetime-picker` feature, default on), tabs, checkboxes via `Button`, high-DPI awareness, flexbox/grid layouts and tray notifications ([README](https://github.com/gabdube/native-windows-gui), [feature flags](https://docs.rs/crate/native-windows-gui/latest/features)).

**Size.** The README measures the `basic` example at "163kb on disk" and "900kb in memory" in release mode ([README](https://github.com/gabdube/native-windows-gui)). Measured, but by the author, in 2020-2022, and not with a DTP-plus-tabs form.

**Maintenance.** Latest release 1.0.13 on 2022-09-05 ([crates.io](https://crates.io/api/v1/crates/native-windows-gui)). Last commit 2023-02-14; repository last pushed 2024-05-16; 57 open issues and zero issues closed since 2025-01-01 (GitHub API, 2026-11-02). The README calls 1.0 the "3rd and final version" and says development is considered "done" with future work expected in other libraries ([README](https://github.com/gabdube/native-windows-gui)). It depends on `winapi ^0.3`, a required dependency ([dependencies](https://crates.io/api/v1/crates/native-windows-gui/1.0.13/dependencies)), whose last release 0.3.9 is from 2020-06-26 ([winapi](https://crates.io/api/v1/crates/winapi)). Using it alongside `windows` means two parallel Win32 binding crates in one exe.

**Native look.** Yes, real comctl32 controls.

**DPI.** "High-DPI aware" per the README, but through a non-default `high-dpi` feature ([feature flags](https://docs.rs/crate/native-windows-gui/latest/features)) and with open bugs: #313 "high-dpi dpi() leaks a screen device context on every query" (2026-10-17), #301 "Avoid GDI DC exhaustion from calling DPI" (2024-05-16), #299 "set_position doesn't seem to take dpi scaling into account" (2024-05-11) ([issue tracker](https://github.com/gabdube/native-windows-gui/issues)). With no maintainer activity these will stay open.

**Loop integration.** NWG expects you to call `nwg::dispatch_thread_events()`; a `dispatch_thread_events_with_callback` variant and `stop_thread_dispatch` exist ([docs.rs](https://docs.rs/native-windows-gui/latest/native_windows_gui/)). Its controls are ordinary HWNDs so they would also be served by our own `GetMessage` loop, but that mode is not documented.

**License.** MIT ([crates.io](https://crates.io/api/v1/crates/native-windows-gui)).

**GNU target.** The 0.2.1 crate page stated NWG "will not compile on the GNU toolchain" because `comctl32.lib` lacked a required function ([crates.io 0.2.1 mirror](https://crates-io.ganymede-static.progval.net/crates/native-windows-gui/0.2.1)). For 1.x nothing documents GNU support either way: docs.rs lists only `x86_64-pc-windows-msvc`, the repository has no CI workflow directory, and the tracker has no MinGW issues (GitHub API, 2026-11-02). Treat as untested on the dev machine's toolchain.

### 3.3 `egui` / `eframe`

**What it is.** An immediate-mode GUI; "egui itself doesn't know or care on what OS it is running or how to render things to the screen", `eframe` is the official native shell built on `egui-winit` with `egui_glow` or `egui-wgpu` ([README](https://github.com/emilk/egui)).

**Size.** Measured data points from the project's own threads: a release Windows exe with boilerplate only was "~2.5mb" in May 2022 ([discussion #1651](https://github.com/emilk/egui/discussions/1651)); a near-empty native project went from 4.29 MB to 8.82 MB switching glow to wgpu in 2025 ([issue #5889](https://github.com/emilk/egui/issues/5889)); eframe 0.35+ makes wgpu the default and its docs say switching to glow "can significantly reduce your binary size" ([eframe docs](https://docs.rs/eframe/latest/eframe/)). Even the best case is larger than the whole of breakpoint's size budget.

**Maintenance.** eframe 0.37.0 released 2026-10-15 ([crates.io](https://crates.io/api/v1/crates/eframe)); repository pushed 2026-10-30, 954 open issues (GitHub API). The README states: "If you want something that doesn't break when you upgrade it, egui isn't for you (yet)" ([README](https://github.com/emilk/egui)).

**Native look.** No: "If you want a GUI that looks native, egui is not for you" ([README](https://github.com/emilk/egui)). There is no time-picker widget; one would be composed from drag values or text.

**DPI.** Handled by winit's scale factor and `egui-winit`'s `pixels_per_point` ([egui-winit docs](https://docs.rs/egui-winit/latest/egui_winit/)). winit enables process-wide DPI awareness itself unless `with_dpi_aware(false)` is set ([EventLoopBuilderExtWindows](https://docs.rs/winit/latest/winit/platform/windows/trait.EventLoopBuilderExtWindows.html)), which collides with a manifest or an earlier `SetProcessDpiAwarenessContext` call; a second attempt fails with `ERROR_ACCESS_DENIED` ([SetProcessDpiAwarenessContext](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setprocessdpiawarenesscontext)), harmless but a sign the two stacks fight over process setup.

**Loop integration.** `run_native` is a winit application; `create_native` returns "a proxy for your native eframe application to run on your own event loop" with `EframePumpStatus` ([eframe docs](https://docs.rs/eframe/latest/eframe/)), so a bridge is possible but it still means a winit `EventLoop` living next to our `GetMessage` loop. winit windows are restricted to the main thread unless `with_any_thread(true)` is used, and such windows die with their thread ([EventLoopBuilderExtWindows](https://docs.rs/winit/latest/winit/platform/windows/trait.EventLoopBuilderExtWindows.html)).

**License.** MIT OR Apache-2.0 ([crates.io](https://crates.io/api/v1/crates/eframe)).

**GNU target.** wgpu 27.0.2 failed to build for `x86_64-pc-windows-gnu` because of `mach-dxcompiler-rs` (issue opened 2025-10-05, fixed by PR #8430 on 2025-11-19); the maintainer noted the GNU Windows target "has historically been unsupported as the primary Windows target" ([wgpu #8303](https://github.com/gfx-rs/wgpu/issues/8303)). The glow renderer avoids wgpu but is no longer the default.

### 3.4 `slint`

**What it is.** A declarative UI toolkit with its own `.slint` language, compiled to Rust; default backend winit with FemtoVG (OpenGL) and the software renderer compiled in, Skia optional ([cargo features](https://docs.slint.dev/latest/docs/rust/slint/docs/cargo_features/)).

**Size.** Unmeasured for a current desktop build. Slint's own 2021 note gives 6.4 MB for the Rust release build of its printer demo ([Slint, this week 2021-11-15](https://old.slint.dev/thisweek/2021-11-15)); the renderer page calls Skia's disk footprint "heavy" ([Backends & Renderers](https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backends_and_renderers/)).

**Maintenance.** 1.18.1 released 2026-09-21 ([crates.io](https://crates.io/api/v1/crates/slint)); repository pushed 2026-11-02, 570 open issues (GitHub API). Healthy.

**Native look.** Widgets are drawn by Slint. "`fluent` is the default on all platforms"; the `native` style is an alias resolving to `fluent` on Windows; only the `qt` style uses real toolkit rendering and needs Qt installed ([Style](https://docs.slint.dev/latest/docs/slint/reference/std-widgets/style/)). A `TimePickerPopup` exists since Slint 1.7 and follows Material Design ([TimePickerPopup](https://docs.slint.dev/latest/docs/slint/reference/std-widgets/misc/timepicker/), [1.7 release post](https://slint.dev/blog/slint-1.7-released)).

**DPI.** The API separates logical and physical pixel types and scale factor is applied by the backend ([slint docs](https://docs.rs/slint/latest/slint/)).

**Loop integration.** `ComponentHandle::run` and `run_event_loop` own the loop and must run on the main thread for most backends ([slint docs](https://docs.rs/slint/latest/slint/)). `BackendSelector` offers `with_winit_event_loop_builder` and `with_winit_custom_application_handler` ([BackendSelector](https://docs.rs/slint/latest/slint/struct.BackendSelector.html)), and `slint::platform` lets you implement a whole platform ([slint docs](https://docs.rs/slint/latest/slint/)). Hosting Slint inside an existing Win32 loop is possible only through those escape hatches.

**License.** "GPL-3.0-only OR LicenseRef-Slint-Royalty-free-2.0 OR LicenseRef-Slint-Software-3.0" ([crates.io](https://crates.io/api/v1/crates/slint)). The Royalty-free licence covers desktop apps but requires attribution: either the `AboutSlint` widget in an About dialog reachable from the top-level menu, or the Slint badge on a public download page ([Royalty-free licence 2.0](https://github.com/slint-ui/slint/blob/master/LICENSES/LicenseRef-Slint-Royalty-free-2.0.md)). GPL would change breakpoint's MIT distribution terms.

**GNU target.** The Skia build "requires Visual Studio 2022" ([Backends & Renderers](https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backends_and_renderers/)), so Skia is MSVC-only; the default FemtoVG/software pair has no documented GNU blocker, and the `winit-femtovg-wgpu` variant inherits the wgpu caveat above.

### 3.5 `iced`

**What it is.** An Elm-style cross-platform GUI with `iced_wgpu` as renderer and `iced_tiny_skia` as software fallback, shelled by winit ([README](https://github.com/iced-rs/iced)).

**Size.** Unmeasured; no current primary figure found.

**Maintenance.** 0.14.0 released 2025-12-07 after 0.13.1 on 2024-09-19 ([crates.io](https://crates.io/api/v1/crates/iced)); repository pushed 2026-11-01, 365 open issues (GitHub API). The README and docs call it "experimental software" ([README](https://github.com/iced-rs/iced), [docs.rs](https://docs.rs/iced/latest/iced/)).

**Native look.** No; built-in themes.

**DPI.** Via winit; iced's docs do not describe it ([docs.rs](https://docs.rs/iced/latest/iced/)).

**Loop integration.** `iced_winit::run` runs a `Program` on winit; a `conversion` module exists "for users who implement a custom event loop" ([iced_winit](https://docs.rs/iced_winit/latest/iced_winit/)). Same main-thread and dual-loop issues as eframe.

**License.** MIT ([crates.io](https://crates.io/api/v1/crates/iced)).

**GNU target.** Default renderer is wgpu, so the wgpu #8303 caveat applies ([wgpu #8303](https://github.com/gfx-rs/wgpu/issues/8303)).

### 3.6 WebView2 via `wry` (or `tauri`)

**What it is.** `wry` hosts Microsoft Edge WebView2 inside any window implementing `HasWindowHandle`; on Windows "The webview will auto-resize when the passed handle is resized"; `build_as_child` makes it a child window ([WebViewBuilder](https://docs.rs/wry/latest/wry/struct.WebViewBuilder.html)). The README requires "a running event loop" ([wry README](https://github.com/tauri-apps/wry)); ours qualifies. Windows-specific options include `with_theme` (follows the OS for `prefers-color-scheme`), accelerator keys and context menus ([WebViewBuilderExtWindows](https://docs.rs/wry/latest/x86_64-pc-windows-msvc/wry/trait.WebViewBuilderExtWindows.html)). Tauri 2.12.5 adds an app framework on top ([crates.io](https://crates.io/api/v1/crates/tauri)) that we would not need for two pages.

**Size.** Exe delta unmeasured; Tauri's size page claims "very small binaries" without a number ([Tauri: App Size](https://v2.tauri.app/concept/size/)). The browser is not in the exe: the Evergreen WebView2 Runtime "will be included as part of the Windows 11 operating system", "the vast majority of Windows 10 devices" have it, the online bootstrapper is "approximately 2 MB", and the Fixed Version binaries are "over 250 MB" ([Distribute your app and the WebView2 Runtime](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)). Microsoft's own `windows-webview` readme says the same: the runtime "ships with Windows 11 and is installed on most Windows 10 machines" ([windows-webview](https://github.com/microsoft/windows-rs/tree/master/crates/libs/webview)).

**Maintenance.** `wry` 0.57.1 released 2026-10-23 ([crates.io](https://crates.io/api/v1/crates/wry)); repository pushed 2026-10-28, 151 open issues (GitHub API). Microsoft's `windows-webview` 0.100.0 (2026-09-03, MSRV 1.95) is a new first-party alternative built on `windows-window` ([crates.io](https://crates.io/api/v1/crates/windows-webview), [Cargo.toml](https://github.com/microsoft/windows-rs/blob/master/crates/libs/webview/Cargo.toml)).

**Native look.** No, HTML and CSS; a time input is `<input type="time">`.

**DPI.** WebView2 renders at the parent HWND's DPI and auto-resizes with it ([WebViewBuilder](https://docs.rs/wry/latest/wry/struct.WebViewBuilder.html)); our PerMonitorV2 manifest governs the host window.

**Loop integration.** Good: a plain HWND plus our existing loop. The two-way bridge (JS `postMessage` to Rust and back) to load and save `config.json` is extra code the native options do not need.

**License.** `wry` MIT OR Apache-2.0 ([crates.io](https://crates.io/api/v1/crates/wry)); `webview2-com` MIT ([webview2-rs](https://github.com/wravery/webview2-rs)).

**GNU target.** `webview2-com` links `WebView2LoaderStatic.lib` by default, which "doesn't work with the `*-pc-windows-gnu` targets", so GNU builds link the import library and must ship `WebView2Loader.dll` next to the exe or on `PATH` ([webview2-rs README](https://github.com/wravery/webview2-rs)). Tauri's prerequisites say to install the C++ Build Tools and "make sure the MSVC Rust toolchain is the selected default host triple" ([Tauri prerequisites](https://v2.tauri.app/start/prerequisites/)). Workable on GNU for local dev, but it breaks the single-file exe story on that target.

## 4. Cross-cutting notes

**Only one candidate adds no event loop.** `tray-icon` needs a running loop on its thread and dispatches tray callbacks through its own hidden window ([README](https://github.com/tauri-apps/tray-icon), [Windows backend](https://github.com/tauri-apps/tray-icon/blob/dev/src/platform_impl/windows/mod.rs)). Raw Win32 dialogs and `wry` plug straight into the loop we already run. eframe, Slint and iced each bring a winit `EventLoop`; bridging it (eframe `create_native`, Slint `BackendSelector`, iced `conversion`) is possible but adds code, and winit's own DPI-awareness setup collides with a manifest ([EventLoopBuilderExtWindows](https://docs.rs/winit/latest/winit/platform/windows/trait.EventLoopBuilderExtWindows.html), [SetProcessDpiAwarenessContext](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setprocessdpiawarenesscontext)).

**DPI is a solved problem for dialog templates.** PerMonitorV2 in the manifest makes Windows scale `CreateDialog` dialogs and comctl32 v6 assets for us ([High DPI](https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows)). Every GPU-rendered toolkit re-implements this; NWG's implementation has open leaks.

**GNU target.** The `windows` crate links by `raw-dylib` so needs no import libs ([windows-link](https://docs.rs/windows-link/latest/windows_link/)); `winresource` supports `windres` ([winresource](https://docs.rs/winresource/latest/winresource/)). Everything built on wgpu was broken on GNU in late 2025 ([wgpu #8303](https://github.com/gfx-rs/wgpu/issues/8303)), Skia requires MSVC ([Slint renderers](https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backends_and_renderers/)), WebView2 needs a shipped DLL on GNU ([webview2-rs](https://github.com/wravery/webview2-rs)), and NWG's GNU status is undocumented.

## 5. Recommendation

**Use raw Win32 dialog templates through the `windows` crate we already depend on.**

- Smallest exe: zero new crates; the forms are resource data and the controls live in `user32`/`comctl32`. Every GPU toolkit measured here costs more than breakpoint's whole budget (egui 2.5 to 8.8 MB, [#1651](https://github.com/emilk/egui/discussions/1651), [#5889](https://github.com/emilk/egui/issues/5889)).
- Least code for *this* UI: layout lives in a `DIALOGEX` template added with `winresource::WindowsResource::append_rc_content` ([WindowsResource](https://docs.rs/winresource/latest/winresource/struct.WindowsResource.html)); the dialog procedure only reads and writes control state. Time pickers are the stock DTP with `DTS_TIMEFORMAT | DTS_UPDOWN` ([DTP styles](https://learn.microsoft.com/en-us/windows/win32/controls/date-and-time-picker-control-styles)); the first-run wizard is two or three such dialogs in sequence; the nudge popup is `TaskDialogIndirect` with custom buttons ([TaskDialogIndirect](https://learn.microsoft.com/en-us/windows/win32/api/commctrl/nf-commctrl-taskdialogindirect)).
- Native look and free DPI scaling from a two-line manifest (comctl32 v6 plus PerMonitorV2) ([Enabling Visual Styles](https://learn.microsoft.com/en-us/windows/win32/controls/cookbook-overview), [Setting default DPI awareness](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process)).
- No second event loop: modal dialogs pump messages themselves, a modeless settings window needs one `IsDialogMessage` call in our loop ([Using Dialog Boxes](https://learn.microsoft.com/en-us/windows/win32/dlgbox/using-dialog-boxes)); `tray-icon` keeps working because it only needs a loop on the thread ([tray-icon README](https://github.com/tauri-apps/tray-icon)).
- Builds identically on MSVC and GNU ([windows-link](https://docs.rs/windows-link/latest/windows_link/), [winresource](https://docs.rs/winresource/latest/winresource/)).
- Cost accepted: `unsafe` FFI and verbose message handling. Keep it in `platform/` behind a small `Settings` struct so `core/` never sees an HWND. If a hand-drawn popup is ever wanted, Microsoft's `windows-window` 0.100 (`pump()` mode, MSRV 1.95) is the lightest helper ([windows-window](https://github.com/microsoft/windows-rs/tree/master/crates/libs/window)).

**Runner-up: WebView2 via `wry`.** It is the only other candidate that attaches to a plain HWND under our existing loop ([WebViewBuilder](https://docs.rs/wry/latest/wry/struct.WebViewBuilder.html)), it is actively maintained (0.57.1, 2026-10-23), HTML makes a two-page form quick to write, and the browser engine is a shared system component rather than exe bytes ([WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)). It loses to raw Win32 because it is not native, needs a JS-to-Rust bridge for config, depends on the Evergreen Runtime being present, and on the GNU target has to ship `WebView2Loader.dll` beside the exe ([webview2-rs](https://github.com/wravery/webview2-rs)). Revisit if the settings UI grows beyond a few pages; `windows-webview` 0.100 from Microsoft is the first-party option to compare at that point.

**Why not the others.** NWG would be the least code for a native form and its 163 KB claim is attractive, but it is frozen (last release 2022, zero issues closed since 2025, "done" per its README), has open DPI leaks, pulls a second binding crate (`winapi` 0.3.9, 2020), and its GNU status is undocumented ([README](https://github.com/gabdube/native-windows-gui), [crates.io](https://crates.io/api/v1/crates/native-windows-gui)). egui, Slint and iced all cost megabytes, draw non-native widgets, bring a winit loop, and sit on wgpu or Skia with GNU-target caveats; Slint additionally requires attribution under its royalty-free licence ([Royalty-free 2.0](https://github.com/slint-ui/slint/blob/master/LICENSES/LicenseRef-Slint-Royalty-free-2.0.md)).
